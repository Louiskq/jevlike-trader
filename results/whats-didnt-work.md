# What didn't work

Written by hand (not generated by `scripts/evidence.py`). Every item comes from the PIPELINE.md
log or the "caught mistakes" entries in DECISIONS.md; numbers in brackets point to the other
files in `results/`.

## In the runs

- **R2 stopped early on a stale feed (2026-10-09).** After 2 hours of trading with the real
  model, the book feed went quiet without disconnecting; the bot's ping came after 20 s, past
  the 15 s stale limit, and the stale-book kill stopped it at 16:18 UTC. A stale stop was
  permanent then. Fixed in M7: a stale-book kill now cancels, flattens and pauses, and resumes
  after 60 s of steady books; a socket that answers pings but sends no books is dropped. The
  pause and resume have not happened in a live run since (0 stale pauses in R3, R5, R6; see
  drills.md).
- **The first drill left a position open (2026-10-08 UTC).** DNS failed about 2 minutes into
  the first loss-limit drill. The stale-book kill fired and no stale trade was made, but both
  flatten attempts failed while the network was down, leaving a 0.00017 BTC short and a
  "position UNKNOWN" report. The user closed it by hand in the testnet UI. Fixed in M6 (flatten
  retry after the network returns); that fix has not been drilled live (drills.md).
- **R5, the first live maker run, was killed after 14 minutes (2026-10-11).** Three modifies in
  a row were refused (`Attempted to modify to invalid new order`) and the order-error kill
  fired. It ended safe: flat, no open orders, reconcile OK. The cause, found from the run's
  events and a one-order testnet probe: Hyperliquid refuses a modify that changes an order's
  side and leaves the old order resting. M8 had shipped a maker that changed side by modify,
  and the paper and fake venues used in the tests accepted it. Fixed in M9 (a side change is a
  cancel plus a new post-only order). R6 then ran its full hour with 26 side-change cancels and
  0 order errors.
- **The model showed no skill.** In every run report the decider's Brier was worse than or
  level with the running base rate at 30, 60 and 300 s; with block-bootstrap intervals, no run
  or horizon shows it beating the baseline (calibration.md). Its probabilities leaned the wrong
  way for the period: on the first check (2026-10-08, placeholder prompt) the mean `p_up` was
  0.626 with 18 of 20 answers above 0.5; in R3 and R6 its mean `p_up` (0.35 to 0.42 across
  runs and horizons) was below the share of up labels (0.50 to 0.64) (calibration.md). The prompts are still the assistant's drafts; the user has
  not edited them.
- **The confident tail was not better.** In R3 at 60 s, the decisions past the trading gate
  0.60 scored Brier 0.2792, against 0.2737 for all decisions together (baselines.md, A3).
- **Every live run lost money after fees**, mostly to fees in the taker runs (pnl.md). This was
  expected for a short-horizon bot at minimum size.

## Not done

- No overnight run: the user decided on 2026-10-10 that 2 hours unattended was enough for now
  (unattended.md). In that run memory rose slowly and had not levelled off after 2 hours.
- The wifi-off drill was never done on purpose; the only network-loss evidence is the
  accidental DNS failure above, before M6 and M7 (drills.md).
- No extra real-model run to reach a few thousand scored decisions (plan item E7, the user's
  choice), so the sample is too small to claim skill or its absence.

## Mistakes caught before they reached a run (DECISIONS.md)

By the reviewer:
- M1: non-finite env values (`MAX_DAILY_LOSS_USD=nan` disabled the loss kill); out-of-range
  probabilities reached calibration; fills deduplicated on (oid, ts, sz) lost real fills; the
  daily-loss baseline reset on restart.
- M2: a trade after the kill switch tripped mid-decision; float residue (about 4e-19 BTC) read
  as a position and silently blocked one side; `run()` hung after the stale watchdog tripped; a
  hung model got a new call every snapshot; a double kill-switch event; WAL files not ignored.
- M3: the dashboard stalled the trader's event loop: with three tabs open and a 300 ms model,
  max stored model latency went from 311 ms to 512 ms, which would have distorted the latency
  table; a port-in-use error printed a false URL.
- M6: one Ctrl-C reported "FLATTEN GAVE UP"; `--seconds` cut the flatten retry short; a second
  Ctrl-C waited on a blocked network thread.
- M7: a socket that answered pings but sent no books was never dropped, and an existing test
  locked that bug in; "(paused at the end)" could never print; DECISIONS.md still described a
  permanent stale stop.
- M8: the maker's own quote leaked into the model's input and the labels; the 20 order actions
  a minute limit could be broken (22 in 20 s in a probe); paper missed adverse fills just
  before a modify; read rate limits were only logged; maker settings could stop the taker.
- M9: a refused modify would have been resent at every decision; a successful side-change
  cancel did not reset the order-error count.

By the builder: a close that floored 0.00015999... BTC to 0.00015 and left one lot open (M2);
decision mids that included the maker's own quote (M8).

By deliberate bugs that passed every test (reviewer break-it checks), each later caught by a
new test: 1 in M1, 4 in M2, 5 in M3, 1 in M6, 2 in M7, 3 in M8.

## Process

- The user merged PR #6 before its review fixes reached main, so a follow-up PR (#7) carried
  them. The orchestrator once pushed a records commit straight to main by mistake (2026-10-04);
  it was disclosed and not reverted.
- GitHub blocked a push that exposed a private email address (M8); the unpushed commits were
  re-authored with the noreply address.
- Cluster access from the VM depended on a short-lived certificate. Device codes expired
  unapproved several times, and for R6 the model was relayed through the Mac, which added a
  hop to the model latency (latency.md). A stale port forward from an earlier session also had
  to be found and replaced.
- Review agents stalled or failed and had to be restarted (M4 twice, M9 twice), and the M8
  builder hit a usage limit once.
